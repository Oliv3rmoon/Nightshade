# Download sources and RomM

Games on a server in your network, shown in the Library and downloaded to the console to play.

## Quick start with RomM

Download sources and save sync both work with a [RomM](https://github.com/rommapp/romm) server in your network (5.0.0 or newer for the save sync). In short:

1. **Put the games on the server.** Games go to RomM's library under `roms/switch/`: a game as one `.nsp` or `.xci` file, or as a folder with the game's file, its updates in `update/` and its DLC in `dlc/`. Then start a scan in RomM (its **Scan** page) so it lists them.
2. **One RomM user per person.** Each person who plays on the console gets a user of their own in RomM; their save data stays apart on the server.
3. **Downloads.** In RomM, create a client API token (your profile, **Client API tokens**) with the scopes `platforms.read` and `roms.read`. Write `/data/nightshade/config/remote/sources.json` over FTP with the server's address and that token (see [Download sources](#download-sources)), start an FTP server on the console on port 2121 (ftpsrv), and open **Settings > Downloads**: the server and its games show up, and the Library lists them.
4. **Save sync.** Open **Settings > Save sync**, Cross on a profile and choose the server. Scan the QR code with your phone, sign in to RomM as that profile's user and approve the code. From then on the profile's save data is synced before and after each game (see [Save sync](SAVES.md#save-sync)). Pairing uses the server from `sources.json`; without download sources, fill in `save-sync.json` over FTP instead. The save sync does not need the FTP server.

## Download sources

A download source is a server in your network that has games, such as a [RomM](https://github.com/rommapp/romm) server. Its games show up in the Library without taking any space on the console. A game is downloaded to the game files folder when you want it; from then on it is a game on the console like one you copied there. Nothing is streamed, unless you set a source to stream its games (see [Playing a game where it lies](#playing-a-game-where-it-lies)). **Downloads need an FTP server running on the console** (port 2121, see below): it writes the downloaded files.

- **Set them up.** Make sure an FTP server runs on the console, then save `/data/nightshade/config/remote/sources.json` on the console (over FTP, like the keys) and open **Settings > Downloads**, or reopen ProsperoEden. It lists the sources, each with its `"type"`, a `"name"` for the menu and what that type needs (see [RomM](#romm) for a RomM server):

  ```json
  { "sources": [
      { "type": "romm", "name": "Home", "url": "http://192.168.1.20:3000", "token": "rmm_..." },
      { "type": "romm", "name": "Office", "url": "https://games.example.org", "token": "rmm_..." }
  ] }
  ```

  **Settings > Downloads** shows each source, whether it answered, and why not when it did not, and the FTP server's port. Without a source it shows what the file is called, with an example for a RomM server. When you ask it to read the lists again (Cross on a source), it says when they are in.
- **The Library.** The sources' games are listed with the console's own, by name, with their cover. A game that is not on the console has a darker cover with a cloud, and instead of NSP or XCI the line under it names its source (or how many have it), or says **Queued**, how far its download is, or **Download failed**. Its details name its sources. The same game on several sources is listed once, and a game that is on the console already is not listed again. Its settings, mods and console mode are there once it is downloaded.
- **Which game is which.** Each source says what it knows of a game: its title ID, its ids at metadata providers (IGDB, ScreenScraper and the like) and whether its name comes from such metadata. Two sources' games are the same game when the first of these that both know agrees: the title ID, then an id at a provider both have one of, then the name (when both names come from metadata; case, accents and punctuation do not count), else the file name. A game on the console is the source's game when it has the file name the source gives it (a downloaded one does), else when their title IDs agree (when the source knows one), else by its name.
- **Play.** Cross on a game that is not on the console downloads it first. A ring shows how far it is and the time left, and the game starts once all of it is there. Circle lets it download in the background without starting it; Square cancels it. When several sources have the game, ProsperoEden asks which one first. (A game of a source set to stream starts at once instead: see [Playing a game where it lies](#playing-a-game-where-it-lies).)
- **Download ahead.** Square on such a game puts it in the download queue, and Square again takes it out. The queue downloads one game at a time while the menu is open, also after ProsperoEden was closed and opened again. **Settings > Downloads** lists it: Square cancels a download, Cross tries a failed one again, and Cross on a source reads the sources' game lists again (also done by itself when the menu opens after more than 15 minutes).
- **Where the files go.** A downloaded game gets a folder of its own in `roms/`, `roms/<game>/`, with the game's file and its updates and DLC in it, as a game you copy to the console in a folder. The folder is named after the game's file, without its extension and the tags dumps carry (`[0100...]`, `[v0]`, `(USA)`): `My Game [0100...][v0].nsp` goes to `roms/My Game/`. What a source counts as the game, an update or DLC is up to it (a RomM server: its file categories). A game downloaded from a source keeps the file name it has there. Only `.nsp` and `.xci` files are downloaded, and an entry without a game file (an update or DLC on its own) is not listed.
- **An FTP server on the console.** Downloads are written by an FTP server running on the console (such as [ftpsrv](https://github.com/ps5-payload-dev/ftpsrv), which most setups have for copying the keys), on port 2121: ProsperoEden hands it the bytes over loopback. Written by the app itself, a game of several gigabytes slowed the drive down to a few MB/s and stopped the menu; from a payload the drive keeps its speed. Without such a server a download fails and says so. `"ftp_port"` next to `"sources"` names another port (etaHEN's own FTP server, for example), and `"ftp_user"` and `"ftp_password"` a sign-in when the server asks for one (else `anonymous`). The server must support `REST` with `STOR`, to go on with a download.
- **Interrupted downloads.** A download is written to `.remote-downloads/` in the game files folder, and once all of the game's files are complete they are moved to the game's folder in `roms/`, so `roms/` only ever holds whole files of whole games. It stops while a game runs and when ProsperoEden closes, and goes on from where it was the next time the menu is open; the last 4 MB are downloaded again then, in case the console lost power while they were written. A cancel deletes what was downloaded (and never touches `roms/`), and what `.remote-downloads/` holds for a game that is not in the queue is deleted when the menu opens, so nothing is left behind. When the drive is full, the download stops and says so, as the FTP server reports it ("No space left on device"); nothing reaches `roms/`, what was downloaded stays in `.remote-downloads/`, and once there is room, Cross on it in **Settings > Downloads** goes on from there (Square cancels it and deletes it). The drive's free space is not checked before a download starts: an app on the console cannot ask for it.
- **Checked as it comes.** RomM does not hash these files, so a download is checked on its way in, as Eden's integrity check checks a game: each NCA of an NSP or XCI against the SHA-256 it is named after, with no keys needed. A file found damaged is deleted and the download fails saying so; trying again downloads it again. A download that goes on reads what it had from the drive first (**Checking** in the queue). What the console's FTP server writes is not read back, and files that are no NSP or XCI are taken as they are.
- **Making room.** A game that a source has can be deleted from the console again: Triangle in the Library, then **Delete from console** (Cross twice). Its file and all of its updates and DLC are deleted, also ones put in its folder by hand, and then its folder in `roms/` once it is empty; its save data, its settings and its mods stay. The Library then lists it as on its sources again, and it can be downloaded any time.

Sign-ins are kept in `sources.json` only, and each is sent to its own source only. They are stored there as plain text, and whoever can reach the console's FTP server can read the file: give a source a token made for it, with only the scopes it needs, rather than your password. A file that is on the console already is never replaced by a download of the same name. Download sources need filesystem access (the payload loader on port 9021), as the game files folder does, and an FTP server on the console (see above). Save data is synced apart from the sources; see [Save sync](SAVES.md#save-sync).

### RomM

`"type": "romm"` is a [RomM](https://github.com/rommapp/romm) server (a current version); as with any source, its games are written by the console's FTP server, which has to run. Its entry in `sources.json` has the server's `"url"` and a `"token"`: in RomM, create a client API token (your profile, **Client API tokens**) with the scopes `platforms.read` and `roms.read`. `"username"` and `"password"` work instead of `"token"`, and `"platform"` names the platform's slug when the server does not call it `switch`. RomM's file categories decide what is the game and what are its updates and DLC; manuals, mods, soundtracks and the like stay on the server. In RomM a game is a folder, with its updates in `update/` and its DLC in `dlc/`. What RomM matched a game to tells it apart: its ids at the metadata providers RomM uses, its name when RomM identified it, and its title ID when the RomM server has the keys to read it.

## Playing a game where it lies

A source can let its games be played straight from it, without downloading them first: add `"stream": true` to its entry in `sources.json`.

```json
{ "sources": [
    { "type": "romm", "name": "Home", "url": "http://192.168.1.20:3000", "token": "rmm_...", "stream": true }
] }
```

- **What it does.** A game that is only on such a source plays at once: Cross in the Library, or on the home screen, starts it instead of downloading it, and its button says **Play**. Square still downloads it to keep it on the console. When several sources have the game, the first one in `sources.json` that streams is used. A game that is on the console plays from the console as always. Without `"stream"` (or with `"stream": false`) nothing changes, and turning it on or off keeps the source's game list. A launcher pack's `launch.request` starts such a game too.
- **What the source needs.** It must be able to send a file from its middle: a RomM server does (it answers HTTP requests for a range of a file). A server that sends files only from their start cannot be played this way; the game stops at its first read that is not at the start, and says so. The source must also give each file's size, as RomM does, and send the file it listed: one that sends another part of it than was asked for, or a file of another size (a file changed on the server: read the source's game list again), stops the game with that reason.
- **What stays on the console.** Saves, shader caches, settings and everything a game writes, as now. Updates and DLC come from what is on the console (`updates/`); the game's own updates and DLC on the source are **not** streamed, so download the game, or copy its update to `updates/`, to play it with them. A streamed game has no game folder in `roms/`, so no mods or presets from one; `mods/<title ID>/` and `cheats/` apply. Its title ID is the one the source knows (RomM knows it when it has the Switch's keys), else the one in its file. It is not added to the recent games on the home screen, and its settings are changed once it is downloaded, as for any game on a source. The save sync syncs it before and after like any game, when the source knows its title ID.
- **The network decides how it plays.** The game asks for pieces of its file as it needs them, and they come over the network: its speed decides how long loading takes and whether the game stutters when it enters a new area. The file is read in 1 MiB blocks and up to 32 MiB ahead of the game, and the last 128 MiB the game read stay in the console's memory, so going back to a place is quick (while graphics memory runs short, only what is read ahead stays). A cable is better than Wi-Fi. A game that reads its file in order (most loading screens) is served by one transfer; one that jumps about starts a new transfer at each jump, and two places read at once take turns in stretches of 4 MiB.
- **Before the game loads.** When you start it, ProsperoEden gives the source 15 seconds to send the start of the game's file, and 45 seconds for all it reads of the game before loading it (its title ID when the source does not know it, its languages and what it holds). A source that is off, unreachable or too slow is told so then: the game does not start, and the home screen says why. Nothing reads the controller in those seconds.
- **When the source goes away.** A transfer the game waits for that fails is tried again after half a second, then 1, 2 and 4 seconds; after five in a row that brought nothing (each may take up to 10 seconds to reach the server, and one that brings no whole 1 MiB block in 20 seconds counts as nothing), the source counts as gone. A transfer that only reads ahead and fails changes nothing for the game: it is tried again later (every 8 seconds at most), so a short loss of the network while the game plays from what is kept does no harm. Once the source is gone, the game's next read of something not kept does not come back to the game, which would get what was never sent: the game stops at once, and the home screen says that the game's download source stopped sending it, and why. It is not started again by itself. While the game is still loading, the load fails instead, with the same reason. Touchpad + L1 leaves a game that waits for the network at once; while it is still loading, ProsperoEden starts again at the launcher if the load has not ended ten seconds later, as for any load that does not end.
- **While a game runs** nothing else is downloaded, as always: only the game's own file is read from its source. It is read with the source's own sign-in, which goes to that source only; the log names the source by its name, never its address or sign-in.

### Reading the log

The lines about a streamed game in `stderr.log` begin with `[ProsperoEden] stream:`.

- `Alpha Quest (Alpha Quest [0100...][v0].nsp, 9.5 GB) is played where it lies on Home: read in 1 MiB blocks, up to 32 MiB ahead, 128 MiB kept`: the game is opened on its source.
- `Alpha Quest: it sent nothing of the game's file within 15 s` (or `it did not send what the game needs to start within 45 s`, or the source's own reason): it did not start (`[ProsperoEden] session failed: The game could not be read from Home: ...`).
- `A read of 64 KiB at 1234 MiB waited 2.1 s for the source (and 3 more since the last such line)`: the game waited that long for the network, a stutter or a long load. It is said at most once every ten seconds. Many of them mean the network is too slow for this game; download it instead.
- `A transfer from 1234 MiB in brought nothing (The connection timed out); asking again in 500 ms (1 of 5)`: a transfer the game waits for failed and is tried again. `The source sent no whole block for 20 s` in it: the network stalled or trickles.
- `A transfer reading ahead from 1234 MiB in brought nothing (...); reading ahead again in 8000 ms`: the network is away while the game plays from what is kept; nothing fails unless the game needs what is not kept.
- `Gave up after 5 transfers in a row brought nothing: ...`, then `The game's reads of what is not kept fail from now on: ...`: the source is gone, and the game stops with that reason (`[ProsperoEden] session failed: The game's download source Home stopped sending it (...)`).
- `This source sends a file only from its beginning, so the game cannot be read where it lies`: the server cannot send a range of a file; download the game instead. `The game's file on the source is ... bytes, not the ... it was listed with` or `The source sent another part of the game's file than was asked for`: the file changed on the server, or the server answers ranges wrongly.
- `Closed after 42.0 min: 310 transfers, 6.2 GB received, 51234 blocks found kept, 2110 waited for, 1800 dropped from the cache`: when the game ended, what came over the network. Blocks *waited for* are the game's reads the network made it wait for; *found kept* are the ones it found in memory.
- `Alpha Quest: Its source does not send games to be played where they lie ...` and the like: the game could not be opened on its source, and did not start.
- `[remote] source Home: its games are played where they lie`: the menu found a source set to stream (said once, when it reads the source's entry the first time or when `"stream": true` is added).
